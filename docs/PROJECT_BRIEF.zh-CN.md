# RunFix 项目简介

> 面向科研代码的自主运行诊断、环境修复与实验复现 Agent
>
> 版本：1.0.0 · 语言：Python 3.10+ · 许可：MIT · 仓库：<https://github.com/liaooss/RunFixMCP>

本文是写给评审与初次接触者的完整介绍。工程细节见 [ARCHITECTURE.md](ARCHITECTURE.md)，
逐模块的现状核查见 [CURRENT_STATE_AUDIT.md](CURRENT_STATE_AUDIT.md)。

---

## 1. 一句话说明

**RunFix 接收一个科研代码仓库，自主完成“理解项目 → 诊断环境 → 定位根因 → 受控修复 → 运行验证 → 判定是否复现”的闭环，
并且对每一步结论都给出可核查的证据，而不是一句“跑通了”。**

关键词：科研代码复现、环境诊断、根因分析、事务式修复、MCP、可复现评测。

---

## 2. 背景：三个断层

科研人员复现一篇论文的代码时，通常不是卡在一个点上，而是连续卡在三个断层的交界处：

| 断层 | 典型症状 | 现有工具的局限 |
| --- | --- | --- |
| **环境断层** | conda/pip 装完仍报错；CUDA 与 PyTorch 版本不匹配 | 依赖安装器只管装，不判断“装完能不能跑” |
| **代码断层** | `ModuleNotFoundError`、形状不匹配、API 变更 | 报错解释器只解释文本，不结合清单与已安装版本 |
| **结果断层** | `train.py` 退出码 0，但没人知道实验是否真的完成、指标是否合理 | 评测框架通常只跑一次，把“没报错”当成功 |

RunFix 的判断是：**这三件事必须在同一条工作流里解决**，否则每一步的结论都无法被下一步验证。

---

## 3. 目标与非目标

**目标**

1. 给出**可追溯**的诊断：每个根因候选都列出支持事实与反证。
2. 给出**可回滚**的修复：任何文件修改都是事务，失败可自动回滚。
3. 给出**可判定**的复现：用证据阶梯代替“退出码 0”。
4. 给出**可审计**的执行：特权操作进入哈希链，权限只能收紧不能放宽。

**非目标（明确不做）**

- 不是通用依赖安装器，也不替代 conda/pip。
- 不修改系统驱动、不改全局 `PATH`、不提权。
- 不下载数据集/权重/许可资源，除非用户显式授权。
- 不在没有证据时宣称“已修复”或“已复现”。

## 4. 系统架构

```

│  CLI (13 子命令)   MCP Server (stdio, 23 工具)   Web 控制台      │
└───────────────┬───────────────────────────┬────────────────────┘
                │                           │
┌───────────────▼───────────┐  ┌────────────▼────────────────────┐
│      Agent 层              │  │        复现层 (repro)            │
│  policy(策略) brain(LLM)   │  │ understand → plan → run →        │
│  tools(白名单) core(循环)  │  │ metrics → report(证据阶梯)       │
└───────────────┬───────────┘  └────────────┬────────────────────┘
                │                           │
┌───────────────▼───────────────────────────▼────────────────────┐
│                      诊断层 (diagnosis)                         │
│  evidence(证据图)  dependencies(PEP440 子集)  rootcause(排序)   │
└───────────────┬────────────────────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────────────────────┐
│  基础能力层                                                     │
│  scanner  diagnostics  analyzer  validation  patches            │
│  environments  task_manager  sandbox  test_selection            │
└───────────────┬────────────────────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────────────────────┐
│  产品支撑层                                                     │
```

数据流：`项目路径 → scanner/diagnostics → 失败日志 → analyzer → diagnosis(证据图+根因) → 动作(安装/补丁/运行) → 报告 + 审计`。

## 5. 关键设计决策

### 5.1 证据阶梯：拒绝把“退出码 0”当成功

复现结论分七级，每级都有明确的进入条件：

| 级别 | 进入条件 |
| --- | --- |
| `inspected` | 读过仓库 |
| `plan_ready` | 有环境/运行计划 |
| `executed` | 命令跑过（失败也算） |
| `completed` | 退出码 0 **且** 有指标序列或完成标记 |
| `metrics_recorded` | 从输出解析出最终指标 |
| `metrics_matched` | 满足调用方声明的目标值 |
| `reproduced` | 指标匹配 **且** 工作区干净、有 git 提交 |

这是本项目最核心的一条设计：**能力边界由证据定义，而不是由实现者的乐观定义。**

### 5.2 确定性置信度，可复算、可反驳

根因候选的置信度不是模型打分，而是可复算的加权：

```
置信度 = 基础分(按类别)
       + 0.03 × (有效证据条数 − 1)，上限 +0.09
       + 0.06（独立分类器给出同一类别时）
       − 0.12 × 反证条数
       裁剪到 [0.05, 0.98]
```

好处是：任何一条结论都可以被人复算、被消融实验检验（见 §7）。

### 5.3 事务式修复

- 应用前：路径校验 → `git apply --check` → 临时树 AST 语法检查。
- 应用中：独立事务 ID、原文件备份、前后 SHA-256、项目级跨进程锁。
- 应用后：验证失败自动回滚；若文件被他人改过则拒绝回滚并报告冲突。
- 崩溃后：`applying` 状态的事务在下次操作时按哈希判定“恢复”或“标记待复核”。

### 5.4 权限只能收紧

三层：服务端开关（如 `--enable-write`）→ 单次调用确认（`confirm_write`）→ 可选的审批
（`--require-approval`，一次性、带有效期、会过期）。恢复运行时沿用启动时记录的权限，
因此 `--resume` 无法提权。

### 5.5 断点恢复

Agent 每完成一步写一次检查点（观测、事件、工具箱状态、循环位置）。
`runfix agent --resume <run_key>` 从下一步继续，**不会重放**已应用的补丁等副作用。

## 8. 现阶段边界（如实说明）

**未验证**（缺环境或凭据，不做宣称）：

- 真实 Docker 容器 / WSL 发行版内执行（开发机无守护进程、无发行版）；
- LLM 规划与 LLM 生成补丁（无 API key）；
- 真实已发表论文仓库上的准确率（基准集为自建）；
- 浏览器级 UI 与可访问性（只做了 HTTP 层验证）。

**方法论边界**：

- 基准集由作者构造，满分是回归护栏，不是真实世界精度；
- 指标从 stdout/stderr 解析，只写文件或上报到跟踪系统的项目不会被捕获；
- 根因是“有证据的假设”，不是证明。

## 10. 如何自己验证一遍

```powershell
git clone https://github.com/liaooss/RunFixMCP.git
cd RunFixMCP
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\install_windows.ps1          # 创建 .venv、安装、并跑 MCP 自检
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m runfix.mcp.smoke --full
.\.venv\Scripts\python.exe -m runfix bench --ablations
```

三步分别验证：单元/集成正确性、协议级可用性、自身诊断能力的量化与消融。
